# RISC-V PKE 内存分配设计分析报告

## 一、现状概述

项目中存在**两套独立的内存分配系统**，分别管理以页为单位和以字节为单位的分配：

### 1. 页级分配（naive_malloc/naive_free）

- **占顶指针**：`current->user_heap.heap_top`
- **主数据结构**：`process_heap_manager`
- **管理方式**：简单的占顶指针 + 空闲页面数组
- **系统调用**：`SYS_user_allocate_page / SYS_user_free_page`
- **特点**：快速，但不支持小于一页的分配

### 2. 字节级分配（better_malloc/better_free）

- **占顶指针**：`current->user_heap_top`
- **主数据结构**：`m_rib`（包含 alloc_list 和 free_list）
- **管理方式**：链表 + first-fit 分配算法
- **系统调用**：`SYS_user_allocate_mem / SYS_user_free_mem`
- **特点**：支持任意大小分配，但分配速度较慢

---

## 二、设计意图分析

这种双占顶指针设计的初衷是：

- 对于**大块内存**（≥1页）：使用快速的页级分配
- 对于**小块内存**（<1页）：使用字节级分配

**假设的使用模式**：应用程序要么只用 `naive_malloc`，要么只用 `better_malloc`，而**不会混合使用**。

---

## 三、存在的严重问题

### ⚠️ 问题 1：虚拟地址空间冲突（最严重）

#### 问题描述

两个占顶指针都独立地从 `USER_FREE_ADDRESS_START` 开始增长，**没有任何同步机制**。

#### 代码位置

在 [syscall.c](syscall.c) 中：

**页级分配**（第89-98行）：

```c
uint64 sys_user_allocate_page() {
    void *pa = alloc_page();
    // ...
    va = current->user_heap.heap_top;
    current->user_heap.heap_top += PGSIZE;  // ← 占顶指针A增长
}
```

**字节级分配**（第117-122行）：

```c
uint64 sys_user_allocate_mem(int n) {
    // ...
    uint64 alloc_va = current->user_heap_top;
    user_vm_map(...);
    current->user_heap_top += PGSIZE;  // ← 占顶指针B增长
}
```

#### 具体场景

假设执行以下操作序列：

```
操作1: better_malloc(100)     // 字节级
    user_heap_top: 0x00000000 → 0x00001000

操作2: naive_malloc()          // 页级  
    heap_top: 0x00000000 → 0x00001000

        ↓ 冲突！
   同一虚拟地址被分配了两次
```

**结果**：当建立第二个映射时，会**覆盖第一个映射**，导致：

- 数据损坏
- 内存泄漏
- 不确定的运行时错误

#### 测试用例

修改 [app_singlepageheap.c](../../user/app_singlepageheap.c) 来演示问题：

```c
int main(void) {
    // 同时使用两种分配方式
    char *page_mem = (char *)naive_malloc();      // 页级分配
    char *byte_mem = (char *)better_malloc(100);  // 字节级分配
    
    *(byte_mem) = 'A';
    *(page_mem) = 'B';
    
    // byte_mem 可能被覆盖！
    printu("byte_mem[0] = %c\n", *(byte_mem));   // 预期 'A'，实际可能是 'B'
}
```

### ⚠️ 问题 2：pa_to_user_va 函数的范围限制

#### 代码位置

[vmm.c](../../kernel/vmm.c) 第226-237行：

```c
uint64 pa_to_user_va(pagetable_t page_dir, uint64 pa) {
    uint64 map_pa;
    // ❌ 仅遍历到 user_heap_top，无法找到 heap_top 范围中的地址
    for (uint64 va = USER_FREE_ADDRESS_START; va < current->user_heap_top; va += PGSIZE) {
        map_pa = lookup_pa(page_dir, va);
        if (map_pa == 0) continue;
        if (pa >= map_pa && pa < map_pa + PGSIZE) {
            return va + (pa - map_pa);
        }
    }
    return (uint64)NULL;
}
```

#### 影响

在 [syscall.c](../../kernel/syscall.c) 第134行，字节级分配的跨页部分依赖此函数：

```c
if (current->mem_rib.free_list != NULL) {
    start_block = current->mem_rib.free_list;
    start_pa = (uint64)start_block;
    start_va = pa_to_user_va((pagetable_t)current->pagetable, start_pa);
    // ❌ 如果 start_pa 在 (user_heap_top, heap_top) 范围内
    //    pa_to_user_va 会返回 NULL，导致分配失败或错误行为
}
```

### ⚠️ 问题 3：进程退出时的内存泄漏

#### 代码位置

[syscall.c](../../kernel/syscall.c) 第59-73行：

```c
ssize_t sys_user_exit(uint64 code) {
    // ...
    pd *free_item = current->mem_rib.free_list;
    if (free_item != NULL) {
        while (free_item) {
            pd *to_free = free_item;
            uint64 user_va = pa_to_user_va((pagetable_t)current->pagetable, (uint64)to_free);
            
            if (user_va != 0) {  // ❌ 如果 pa_to_user_va 返回 NULL
                user_vm_unmap(...);
            }
            // 如果 user_va == 0，此物理页**永远无法回收**！
            current->mem_rib.free_list = free_item;
        }
    }
}
```

**结果**：当进程退出时，某些物理页面无法被正确释放，造成内存泄漏。

---

### ⚠️ 问题 4：Fork 时的状态不一致

在 fork 操作中，如果父进程同时使用了两种分配方式，子进程继承的两个占顶指针可能不同步，导致：

- 子进程继承的虚拟地址映射与占顶指针指向的地址范围不匹配
- 进一步加重地址冲突问题

---

### ⚠️ 问题 5：跨页分配的复杂性和脆弱性

#### 代码位置

[syscall.c](../../kernel/syscall.c) 第111-172行

在 `sys_user_allocate_mem` 中处理跨页分配的逻辑过于复杂，包含多个潜在的边界条件问题：

```c
uint64 total_needed = sizeof(pd) + n;
uint64 extra_pages = (remaining + PGSIZE - 1) / PGSIZE;

for (uint64 i = 0; i < extra_pages; i++) {
    void *pa = alloc_page();
    uint64 va = current->user_heap_top;  // ❌ 与 naive_malloc 的 heap_top 竞争同一地址空间
    user_vm_map(...);
    current->user_heap_top += PGSIZE;
}
```

**问题**：如果在这个循环中间发生中断或 fork，状态会变得不一致。

## 四、为什么这个设计是错误的

### 1. **违反虚拟内存管理原则**

- 虚拟地址空间应该由** 唯一的占顶指针**管理
- 多个独立的占顶指针会导致**地址空间分割不明确**

### 2. **没有防守的假设**

- 设计假设应用程序不会混合使用两种分配方式
- 但 **fork()、库函数调用等场景天然会混合使用**

### 3. **PA ↔ VA 转换的困难**

- 两个独立的占顶指针使得 `pa_to_user_va` 难以实现
- 目前的实现**不完整且容易出错**

## 五、改进方案

### 方案 A：统一占顶指针（推荐）✅

**设计**：所有分配都共享一个占顶指针

```c
// process.h 中的修改
typedef struct process_t {
    uint64 heap_top;  // ← 统一的占顶指针，用于所有堆分配

    pd *alloc_list;   // 已分配链表
    pd *free_list;    // 空闲链表
    // 移除 process_heap_manager 中的独立 heap_top
    
    // ... 其他字段
} process;
```

**优点**：

- 逻辑清晰，没有地址冲突
- 代码简化
- 易于维护

**缺点**：

- 页级分配的性能优化不复存在（但实际收益有限）

---

### 方案 B：分离虚拟地址空间（次选）

**设计**：为两种分配方式分配不同的虚拟地址范围

```c
#define PAGE_ALLOC_START    0x00100000  // 4MB：页级分配区间
#define PAGE_ALLOC_END      0x01000000  // 16MB

#define BYTE_ALLOC_START    0x01000000  // 16MB：字节级分配区间
#define BYTE_ALLOC_END      0x02000000  // 32MB
```

改进 `pa_to_user_va`：

```c
uint64 pa_to_user_va(pagetable_t page_dir, uint64 pa) {
    // 同时扫描两个范围
    for (uint64 va = PAGE_ALLOC_START; va < PAGE_ALLOC_END; va += PGSIZE) { ... }
    for (uint64 va = BYTE_ALLOC_START; va < BYTE_ALLOC_END; va += PGSIZE) { ... }
    return (uint64)NULL;
}
```

**优点**：

- 保留两套分配系统
- 从根本上避免地址冲突

**缺点**：

- 在虚拟地址空间较小的系统上可能不适用
- 代码改动较多

---

### 方案 C：快速方案（临时修复）

在不改动架构的前提下，**强制禁止混合使用**：

```c
// 在每个分配时检查
uint64 sys_user_allocate_page() {
    if (current->user_heap_top != USER_FREE_ADDRESS_START) {
        panic("Cannot mix naive_malloc and better_malloc!");
    }
    // ... 继续分配
}
```

**注意**：这不是根本解决方案，只是应急措施。

## 六、验证问题存在的方式

### 测试代码

在 [user/](user/) 目录创建 `test_mixed_alloc.c`：

```c
#include "user_lib.h"

int main(void) {
    printu("[Test] Starting mixed allocation test...\n");
    
    // 分配第一页（字节级）
    char *m1 = (char *)better_malloc(100);
    printu("better_malloc returned: 0x%lx\n", (uint64)m1);
    
    // 分配第二页（页级）
    char *m2 = (char *)naive_malloc();
    printu("naive_malloc returned: 0x%lx\n", (uint64)m2);
    
    // 检查是否冲突
    if (m1 && m2) {
        uint64 page1 = (uint64)m1 & ~(PGSIZE - 1);
        uint64 page2 = (uint64)m2 & ~(PGSIZE - 1);
        
        if (page1 == page2) {
            printu("[ERROR] Address collision detected! Both allocated to 0x%lx\n", page1);
            exit(-1);
        } else {
            printu("[INFO] No collision: 0x%lx vs 0x%lx\n", page1, page2);
        }
    }
    
    exit(0);
}
```

## 七、总结

| 问题                | 严重程度  | 发生概率       | 影响范围        |
|-------------------|-------|------------|-------------|
| 虚拟地址冲突            | 🔴 严重 | 高（混合使用）    | 数据损坏、段错误    |
| pa_to_user_va 不完整 | 🔴 严重 | 中等         | 跨页分配失败、内存泄漏 |
| 进程退出内存泄漏          | 🟡 中等 | 高（长期运行）    | 内存资源耗尽      |
| fork 状态不一致        | 🟡 中等 | 低（无fork测试） | 多进程程序崩溃     |
| 跨页分配脆弱性           | 🟡 中等 | 中等         | 分配失败、数据损坏   |

## 八、建议

### 立即行动（必需）

1. 查阅项目的测试用例，确认是否实际测试了混合分配
2. 如果测试套件有混合分配的情况，则**设计确实存在bug**
3. 采用方案 A（统一占顶指针）进行重构

### 长期改进

1. 为内存管理添加更多的单元测试
2. 考虑集成内存检查工具（AddressSanitizer）
3. 在多进程场景下进行压力测试

---

**结论**：虽然这种双占顶指针设计的初衷是优化性能，但它**在正确性上有严重缺陷**，特别是在混合使用、多进程、以及进程退出等场景下。建议采纳方案
A 进行修复。
